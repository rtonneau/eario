# Eario: instructions for AI coding agents

Eario is a local-first Rust framework for building interactive dashboards and
data exploration tools. A developer describes a dashboard in Rust; it compiles
into one executable that serves a generic Svelte frontend from the loopback
interface. This file is the canonical instruction file; read it before
changing anything.

Read next, as needed:

- `docs/architecture/overview.md`: how the pieces fit, data flow, HTTP API.
- `docs/architecture/security.md`: the local-server threat model.
- `docs/adr/`: why each structural decision was made, and what is still open.
- `docs/project-status.md`: what works today, known limitations.
- `docs/roadmap.md`: what comes next.
- `docs/development/guide.md`: setup, commands, frontend workflow, testing.

## Principles

- **Local-first.** No cloud service, account or network access is required.
  Never add a request to a remote host: fonts, scripts and styles are bundled.
  The one exception is the hub (`eario-hub`), which may contact the GitHub
  hosts listed in `docs/architecture/security.md` over HTTPS, to install and
  update dashboards (ADR 0013).
- **Rust-first.** Dashboard authors write Rust only. The frontend is generic
  and must not contain logic of a particular dashboard or scientific domain.
- **One source of behaviour.** `eario_runtime::App` holds the application
  services. HTTP handlers and MCP tools are thin adapters over it. Never
  implement business logic in an adapter.
- **Serializable specification.** A dashboard is a `DashboardSpec` (data, no
  code). Keep executable callbacks out of it.
- **Small and explicit.** Prefer two clear lines over one clever line. Add an
  abstraction when a second concrete use exists, not before.

## Repository

```text
crates/eario           Facade: Dashboard builder, widgets, prelude. The public API.
crates/eario-core      DashboardSpec, identifiers, contract types. No heavy dependency.
crates/eario-data      Readers (CSV, TSV, XLSX), Dataset, queries. Owns Polars.
crates/eario-runtime   App services, HTTP server, security, preferences, embedded frontend.
crates/eario-mcp       Read-only MCP server over App. Optional (feature `mcp`).
crates/eario-hub       Hub: supervisor, HTTP API, GitHub installs, `eario-hub` executable (ADR 0011, 0013).
frontend/              Generic Svelte 5 + TypeScript frontend, built by Vite.
examples/              hello-dashboard, data-explorer. Use the public API only.
fixtures/              Synthetic test data, generated by `cargo xtask fixtures`.
xtask/                 Development commands.
docs/                  Architecture, ADRs, roadmap, status, development guide.
```

### Crate boundaries

Dependencies point one way: `eario` → `eario-mcp` → `eario-runtime` →
`eario-data` → `eario-core`. `eario-hub` depends on `eario-runtime` and
`eario-core` only, and no crate depends on it.

- `eario-core` depends on serde only. No Polars, Axum or Tokio types.
- Polars types appear only in `eario-data` (and where `DataFrame` is passed
  through). Functions of `eario_data::query` return `eario-core` types.
- `eario-runtime` must not depend on `eario-mcp` or on agent integrations.
- `eario-hub` is the only crate that starts a process on request (a
  dashboard) and the only code that contacts a non-loopback host (`github.rs`). Its logic is
  in `supervisor.rs` and `remote.rs`; `http.rs` and `cli.rs` only adapt
  requests to it.
- Crates planned but not created yet are listed in `docs/architecture/overview.md`.
  Do not create an empty crate to match the plan.

## Commands

Run from the repository root. They work on Windows and Linux; do not add
scripts that need Bash.

```text
cargo xtask setup       Install frontend dependencies (npm ci)
cargo xtask frontend    Build the frontend into crates/eario-runtime/frontend-dist
cargo xtask gen-types   Regenerate frontend/src/lib/generated from the Rust contract types
cargo xtask fixtures    Regenerate fixtures/
cargo xtask test        Rust tests and frontend tests
cargo xtask check       CI checks: fmt, clippy, tests, docs, svelte-check, vitest
cargo xtask e2e         Browser tests (Playwright, Chromium) with axe accessibility checks
cargo xtask bench       Benchmarks; writes docs/benchmarks/<date>.md
cargo xtask dist        Frontend build, then release build of data-explorer
cargo deny check        Dependency licences and advisories (needs cargo-deny installed)
```

CI also runs `cargo xtask e2e`, `cargo deny check`, and the tests with the
minimum supported Rust version (`rust-version` in `Cargo.toml`, 1.95). Do not
use a language feature or dependency that needs a newer compiler without
raising it on purpose.

Run one example: `cargo run -p data-explorer -- fixtures/csv/measurements.csv`.

## Coding conventions

Rust:

- Format with `cargo fmt` (configuration in `rustfmt.toml`). Clippy must pass
  with `-D warnings`.
- No `unsafe` (forbidden workspace-wide).
- No `unwrap()` or `expect()` outside tests. Where an invariant makes failure
  impossible, restructure the code so the compiler sees it, or document the
  invariant next to the call.
- Errors are `thiserror` enums with messages a dashboard user can act on:
  name the file, worksheet or column. Each has a stable `code()`.
- Never discard an error silently. If ignoring one is correct, say why in a
  comment on that line.
- Log with `tracing`, using structured fields (`tracing::info!(dataset = %id, ...)`).
  `println!` is reserved for the start-up and shutdown lines of `server::run`.
- Document every public item. `missing_docs` is a workspace warning and CI
  denies warnings.
- CPU-bound work (Polars, parsing) must not run on the async runtime: call it
  through `tokio::task::spawn_blocking`, as `http::blocking` does.
- Avoid cloning data. Cloning a `DataFrame` is cheap (shared columns); copying
  its values is not.

Frontend:

- Svelte 5 runes, TypeScript strict. `npm run check` must report no warning.
- Only `src/lib/api.ts` calls `fetch`. Only `src/lib/chart-option.ts` knows
  the ECharts option format.
- Colours come from the tokens in `src/app.css`; do not hard-code a colour in
  a component.
- Every input has a label; state changes that matter are announced
  (`role="status"`, `role="alert"`).

## Keeping the contract synchronized

The types in `eario-core` (`spec`, `payload`, `filter`, `id`) are the
frontend/backend contract. After changing one:

1. Run `cargo xtask gen-types` and commit the changes in
   `frontend/src/lib/generated/`. Never edit those files by hand.
2. Run `npm run check` in `frontend/`. Adding a `ComponentKind` variant fails
   the type check until `frontend/src/lib/registry.ts` has a renderer for it.

CI regenerates the bindings and fails if they differ from what is committed.

## Adding things

- **A component kind:** variant in `eario_core::ComponentKind` (with its
  `dependencies()`), data in `ComponentData`, a branch in
  `App::component_data`, a constructor in `eario::widgets`, a Svelte component
  and its `registry.ts` entry, tests at each level.
- **A data format:** implement `eario_data::TableReader`, register it in
  `ReaderRegistry::default`, add a fixture and an import test.
- **A dependency:** justify it in the pull request (what it replaces, its
  licence, its maintenance). Declare it in `[workspace.dependencies]` with the
  narrowest feature set. Heavy or optional integrations go behind a Cargo
  feature. Do not invent an API: read the crate's documentation or source.

## Testing

- Test behaviour through public interfaces, not implementation details.
- A bug fix comes with a test that fails without it.
- Rust: unit tests beside the code; `crates/eario-data/tests/import.rs` for
  fixtures; `crates/eario-runtime/src/http_tests.rs` for the HTTP API and its
  security; `crates/eario/tests/end_to_end.rs` for a real server.
- Frontend: Vitest files beside the code (`*.test.ts`).
- Browser: Playwright specs in `frontend/e2e/`, driving the real examples.
  Call `expectAccessible` after each new state; never disable an axe rule.
- Fixtures are synthetic. Never commit real laboratory, personal or
  confidential data.
- Never state that a test or check passed unless you ran it and saw it pass.
  Report failures with their output.

## Security expectations

- The server binds to `127.0.0.1` only. Do not add an option that binds
  elsewhere without an ADR.
- Every API route sits behind the Host/Origin check and the session token.
  New routes go through `http::router` so they inherit both.
- User-supplied names are never used as file-system paths.
- No endpoint or tool may execute a command, a script, or code supplied at
  runtime.
- One bounded exception: the hub (`eario-hub`) starts and stops installed
  dashboards, and installs, updates and rolls them back from signed GitHub
  releases (ADR 0013). Its routes read no body or query; every parameter is
  a path segment validated strictly (`eario_core::is_slug`, `is_repo` over
  `{owner}/{repo}`, 64 lower-case hex for a SHA-256, `on|off`), never a
  path, a URL, an executable or arguments. It starts only its own copy in
  `bin/<slug>/`, after checking size, SHA-256 and launch protocol version
  against the registry, with `--eario-child <run file>` and nothing else. It
  runs a downloaded file, for `--eario-manifest` only, once its signature,
  hash and key are verified, and installs it once the user confirmed the
  preview by its SHA-256 (or, for the one-step update, when the key is pinned or
  already accepted and the version strictly newer). Do not widen the exception (a path, a URL,
  arguments, another host, another executable) without an ADR; see
  `docs/architecture/security.md`.
- MCP tools are read-only and return bounded results. A mutating or expensive
  tool needs an explicit permission design first (see ADR 0009).

## Documentation

- Update `docs/project-status.md` when a capability is added or a limitation
  is found, and `docs/roadmap.md` when priorities change.
- Record a structural decision as a new ADR in `docs/adr/`.
- The README lists only what works. Planned features are labelled as planned.
- Only document commands that exist.

## Definition of done

A change is done when:

1. `cargo xtask check` passes locally, and `cargo xtask e2e` when the
   frontend or an example changed.
2. New behaviour has tests; changed contract types have regenerated bindings.
3. Public items are documented; affected documents in `docs/` are updated.
4. No new dependency is unexplained, no secret or private data is added.
5. The summary of the change states what was verified and what was not.
